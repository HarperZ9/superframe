# superstack contract v0

Contract id `superstack/0`, release 0.2.0. Text: CC BY 4.0. Code: FSL-1.1-MIT from v0.2.0; v0.1.0 remains MIT.

This contract lets different renderers and sound engines produce the same bytes from the same scene, and lets anyone check whether they did. It fixes six things every producer shares: a scene description, one canonical byte form with SHA-256, one seed rule, one integer clock, one receipt with two verdicts, and one reconcile check. Pixels and sound follow the same rules.

Three implementations carry the contract, one file each: `superstack.py` (Python 3.11 or later, standard library only), `superstack.mjs` (an ES module with no dependencies, for browsers and Node 20 or later) and `superstack.hpp` (C++23, header only, standard library only). Every rule below has test vectors in `vectors/`, and all three files pass every vector.

The key words MUST, MUST NOT, SHOULD and MAY follow RFC 2119.

## 1. How to read this document

- Section numbers match the `spec` field in each vector file.
- Where this text and the vectors disagree, one of them has a bug. File it; neither silently wins.
- The vectors were generated by `tools/make_vectors.py` from the Python file. The JavaScript and C++ files were written separately and reproduce every value. Some expected values come from outside the contract: SHA-256 from Python's `hashlib` and the FIPS 180 test strings, the BS.1770 reading of a full-scale sine, the site's seed module, and the scene hashes recorded by the 3 October 2026 proof.
- Each implementation also has paired mutations (`tests/mutations.json`): a one-line break per rule that its vector file must catch. Section 10 covers them.

## 2. Scene and frame IR

### 2.1 Pixel scene: `superstack.scene/1`

A pixel scene is a JSON object. The fields below are the ones the reference scene uses (`examples/pixels/scene.json`).

| Field | Meaning |
|---|---|
| `kind` | `"superstack.scene/1"` |
| `seed` | Seed string (section 4). Optional |
| `t_flicks` | Time of the frame in flicks (section 5). Integer, at least 0. Defaults to 0 |
| `frame` | `width`, `height` (positive integers), `pixel_center` (0.5: samples sit at pixel centres), `origin` (`"top-left"`) |
| `camera` | `eye`, `target`, `up`, `fovy` (radians, vertical) |
| `meshes` | Geometry in a fixed order. `quad` with four `corners`, a `normal` and an `albedo`; `box` with `center`, `half` and `albedo` |
| `lights` | `directional` lights with `dir` and `intensity` |
| `shade` | `model` (`raw-lambert-ao/1`), `ambient`, `clamp`, `encode` (`u8-round-half-up`) |
| `ao` | `estimator` (`rt-cosine-hemisphere`), `samples`, `radius`, `hash` (`raw-pixel-hash/1`), `origin_offset`, `t_min` |
| `outputs` | The canonical channels to produce, from section 2.3 |

The scene spells out conventions that usually hide in code: the pixel centre, the origin, the u8 encode, the ray offset and `t_min`. The proof needed each one to reach byte equality across three engines.

### 2.2 Sound scene: `superstack.sound/1`

A sound scene is a JSON object with `kind` `"superstack.sound/1"`, a `seed`, an integer `rate` from the rate set (section 5), `channels` (1 or 2) and a positive integer `duration_samples`. All other fields belong to the producer. The example scene (`examples/sound/sound.json`) adds a scale, a voice count, gains and envelope lengths in samples.

### 2.3 Canonical media forms

The receipt hashes media in these raw forms, never in containers:

| Channel | Bytes |
|---|---|
| `frame.rgb8` | RGB, 8 bits per channel, rows top-down, no padding |
| `frame.rgba8` | RGBA in the same layout |
| `ao.f32` and other float channels | IEEE 754 float32, little-endian, rows top-down |
| `mask.u8` | One byte per pixel, 0 or 1 |
| `pcm.s16` | Signed 16-bit little-endian PCM, interleaved, at the scene rate |

Container files (PNG, WAV, MP4) MAY appear in `outputs` as secondary hashes. An encoder change alters a container hash without changing a pixel or a sample, so a container hash MUST NOT be the `content_sha256`.

### 2.4 Validation and refusal

`validate_scene` returns sorted error codes; an empty list means valid. Codes: `type`, `kind`, `seed`, `t_flicks`, `frame`, `rate`, `channels`, `duration_samples`.

A backend that cannot draw a scene MUST refuse it and say why. Its receipt carries a tolerance verdict of `unverifiable` with a `reason`. It MUST NOT draw an approximation and present that as the scene. raw-native renders one built-in scene, so its adapter compares the geometry and refuses anything else.

## 3. Canonical JSON v2

Canonical JSON is the one byte form for anything that gets hashed. Two implementations that agree on a value MUST produce the same bytes for it.

### 3.1 Structure

- UTF-8, no byte order mark, no whitespace between tokens.
- Object keys sorted by Unicode code point. This equals byte order of the UTF-8 encoding. It differs from UTF-16 code unit order, which JavaScript's default `sort()` uses, for keys above U+FFFF.
- `null`, `true` and `false` as JSON literals.
- Duplicate keys are an error.

### 3.2 Numbers

Every number is an IEEE 754 binary64 value.

- An integer type (a Python `int`, a C++ `int64_t`, a JavaScript `BigInt`) is written as decimal digits. Its magnitude MUST NOT exceed 2^53 - 1; an implementation MUST reject a larger one.
- Any other number is written as its shortest round-trip decimal, in plain positional notation: no exponent, no leading zeros beyond a single `0.`, no trailing zeros after the point, and no point at all when the value is integral.
- Negative zero is written `0`.
- NaN and the infinities are errors.

Shortest round-trip digits come from `repr` in Python, `Number.prototype.toString` in JavaScript and `std::to_chars` in C++. All three choose the closest shortest digit string, so they agree.

The rule exists because of a finding in the proof. Python's `json.dumps` writes `1.0` and `1e-07`; JavaScript writes `1` and `1e-7`. Both are valid JSON, and the two give different hashes for the same document. Under v2 every implementation writes `1` and `0.0000001`.

| Value | Canonical |
|---|---|
| `1.0` | `1` |
| `1e-07` | `0.0000001` |
| `-0.0` | `0` |
| `1e21` | `1000000000000000000000` |
| `2^53` as a float | `9007199254740992` |
| `2^60` as a float | `1152921504606847000` (shortest digits, then zeros) |
| `5e-324` | `0.` followed by 323 zeros and `5` |

### 3.3 Strings

- `"` and `\` are escaped as `\"` and `\\`.
- U+0008, U+0009, U+000A, U+000C and U+000D are escaped as `\b`, `\t`, `\n`, `\f` and `\r`.
- Every other code point below U+0020 is escaped as `\u00xx` with lowercase hex.
- Everything else, including U+007F, U+2028, U+2029 and `/`, is written as raw UTF-8.
- A lone surrogate is an error. No Unicode normalization is applied.

### 3.4 Hash

SHA-256 (FIPS 180-4) of the canonical bytes, written as 64 lowercase hex digits. `canonical_sha256(value)` is the hash of `canonical(value)` encoded as UTF-8. FNV-1a and other fast hashes MAY bucket and key caches. They MUST NOT appear in a receipt.

### 3.5 Limits

A JavaScript `JSON.parse` turns an integer above 2^53 - 1 into a nearby double without telling anyone, so a JavaScript reader cannot detect an unsafe integer in a document it parsed. Producers MUST NOT write unsafe integers. The C++ parser reads them as doubles, as JavaScript does; Python's reader keeps them as integers and the canonical writer then refuses them.

## 4. Seed rule

### 4.1 `xmur3-mulberry32/1`

A seed is a string. It becomes a 32-bit state through xmur3, and mulberry32 draws from that state.

1. Encode the seed as UTF-16 code units. Let `n` be the number of code units.
2. `h = 1779033703 XOR n`. For each unit `u`: `h = (h XOR u) * 3432918353 mod 2^32`, then rotate `h` left by 13 bits.
3. `h = (h XOR (h >> 16)) * 2246822507`, `h = (h XOR (h >> 13)) * 3266489909`, `h = h XOR (h >> 16)`, all mod 2^32. The result is `seed_u32`.
4. mulberry32 keeps `a = seed_u32`. Each draw: `a = a + 0x6D2B79F5`; `t = (a XOR (a >> 15)) * (a OR 1)`; `t = t XOR (t + (t XOR (t >> 7)) * (t OR 61))`; output `t XOR (t >> 14)`, all mod 2^32.
5. A float draw is `next_u32 / 2^32`, in [0, 1).

This is the site's existing Atelier path (`makeRng`): the vectors include the site module's first five draws for `folded-light`, and every seed in `vectors/seed.json` draws the same stream through the site's `seed.mjs`.

Edge case: the proof's Python contract iterated code points, while the site iterates UTF-16 code units. The two agree on every seed below U+10000 and disagree on any seed with an emoji or another astral character. v0 fixes the rule to UTF-16 code units, so the site's existing seeds keep their streams. A seed with a lone surrogate is an error.

### 4.2 Sub-streams

A named sub-stream uses the seed `seed + "/" + tag`, for example `folded-light/voice-3`. Adding a stream never shifts another stream's draws.

### 4.3 `raw-pixel-hash/1`

For GPU-friendly stateless draws, raw-native's integer hash of a pixel position and a sample index:

```
h = x*374761393 + y*668265263 + s*2246822519        (mod 2^32)
h = (h XOR (h >> 13)) * 1274126177                   (mod 2^32)
h = h XOR (h >> 16)
unit = (h AND 0xFFFFFF) / 16777216
```

### 4.4 Rule ids

Every receipt names its seed rule. Known ids: `xmur3-mulberry32/1` (the default), `raw-pixel-hash/1`, and three legacy rules that keep working under their own names so old artefacts never need re-rendering: `fnv1a32-mulberry32` (the site's `rngFrom`), `studio-engine-lcg/1` and `splitmix-fnv/1` (the site's `audio.js`). A verifier checks `seed_u32` only for the default rule.

## 5. Flick clock

Time is an integer count of flicks. One second is 705,600,000 flicks.

- Frames at `num/den` frames per second last `705600000 * den / num` flicks. The rate is refused when that is not an integer. 24, 25, 30, 48, 50, 60, 90 and 120 fps and 24000/1001, 30000/1001 and 60000/1001 fps all land on integers (30000/1001 fps is 23,543,520 flicks per frame).
- Samples at `rate` Hz last `705600000 / rate` flicks. The rate set is 8000, 11025, 16000, 22050, 32000, 44100, 48000, 88200, 96000, 176400 and 192000 Hz. A sound receipt's rate MUST come from this set.
- At 48 kHz one sample is 14,700 flicks, so a 2 s sound is 1,411,200,000 flicks.
- `t_flicks` and every duration MUST be integers. JavaScript holds integers exactly up to 2^53 - 1, which is about 147 days of flicks.
- Float seconds, frame indices and MIDI ticks convert at the producer's edges. MIDI ticks need the tempo map, which the receipt records.

## 6. Receipt: `superstack.receipt/1`

### 6.1 Fields

| Field | Content |
|---|---|
| `schema` | `"superstack.receipt/1"` |
| `producer` | `{name, version}` |
| `backend` | Which path made the bytes, for example `python-numpy-f32`, `webgl2`, `js-f64` |
| `scene_sha256` | `canonical_sha256(scene)` |
| `seed`, `seed_rule`, `seed_u32` | The seed string or null, the rule id, and xmur3 of the seed under the default rule (null otherwise) |
| `time` | `{base: "flicks", per_second: 705600000, t}` with `t` the scene's `t_flicks` |
| `media` | `{kind: image, width, height, format, transfer}` or the audio block in section 8.6. `kind` is one of `image`, `audio`, `video`, `document` |
| `content_sha256` | SHA-256 of the canonical media bytes (section 2.3) |
| `outputs` | `{name: sha256}` for every file written, containers included |
| `reconcile` | null, or the block in section 6.2 |
| `does_not_prove` | Non-empty list of sentences, each naming something this receipt does not show |
| `receipt_sha256` | `canonical_sha256` of every other field |

An integer field holds a number with an integral value in the safe range: `3` and `3.0` both count, and `true` does not. A required text field holds a non-empty string.

### 6.2 Two verdicts

A receipt reports identity and tolerance separately:

```json
"reconcile": {
  "reference": {"backend": "raw-native-0.4.0-cpu", "content_sha256": "e276..."},
  "identity": "MATCH",
  "tolerance": {"verdict": "verified", "metrics": {...}, "bounds": {...}}
}
```

- `identity` is `MATCH` when `content_sha256` equals the reference's, and `DRIFT` otherwise. It is about bytes only.
- `tolerance.verdict` is `verified` when every metric is within its bound, `refuted` when one is not, and `unverifiable` when the comparison cannot run (no reference, a size mismatch, a scene the backend refused). `unverifiable` MUST carry a `reason`.
- `metrics` and `bounds` record what was measured and what it was held to. Metrics that pass through `log10` or `pow` are rounded half up to 6 decimals (`round6`), so receipts agree across languages; the verdict compares the unrounded values.

Both verdicts are needed. In the proof, one flipped byte read DRIFT and still read verified, because a 1-level change sits inside the tolerance. SwiftShader drew 9 of 65,536 pixels differently (at most 3 levels): DRIFT, verified. The WebGL2 path on the RTX 4090 drew the same bytes as raw-native: MATCH, verified.

### 6.3 Contract tolerances

| Media | Metrics | Default bounds |
|---|---|---|
| `pcm.s16` | `max_abs_lsb`, `exact_frac`, `snr_db` (null when identical) | `max_abs_lsb` at most 2, `snr_db` at least 60 |
| `frame.rgb8` | `mean_abs`, `max_abs`, `exact_pixels_frac` | `mean_abs` at most 1.0 level |
| float channels | `f32_rmse` over a mask | set by the producer |

A producer MAY add bounds. The example pixel check adds coverage mismatch at most 0.5 % and AO RMSE at most 0.02, the bounds the proof fixed before its first comparison.

### 6.4 Verifying a receipt

`verify_receipt` returns sorted error codes; an empty list means the receipt is well formed and its seal holds. It re-renders nothing. Codes:

`type`, `missing:<field>`, `schema`, `does_not_prove`, `time`, `hex:<field>`, `seed_rule`, `seed_u32`, `reconcile:reference`, `reconcile:identity`, `reconcile:verdict`, `reconcile:reason`, `media:kind`, `audio:rate`, `audio:format`, `audio:duration`, `audio:autoplay`, `audio:reduced_sound`, `audio:captions`, `audio:transcript`, `narration:type`, `narration:<field>`, `narration:reference`, `narration:reproducible`, `seal`.

`seal` is checked only when nothing else is wrong.

## 7. Colour

### 7.1 OKLab

Float OKLab with Bjorn Ottosson's published matrices, from linear sRGB, with the sRGB transfer function of IEC 61966-2-1 (breakpoints 0.04045 and 0.0031308, exponent 2.4). These are the same constants as the site's `sense-core` module.

Cube roots come from each platform's maths library, which may differ in the last bit. OKLab values are therefore compared with a tolerance of 1e-9 and MUST NOT be hashed in v0. An integer OKLab for hashed use is planned and not part of v0.

### 7.2 Risk tokens

Status colour reads as liability. Four levels, in order:

| Level | Meaning | Verdict words |
|---|---|---|
| `low` | The claim is verified; acting on it carries little liability | MATCH, VERIFIED, PASS, OK |
| `moderate` | The claim could not be checked; liability is unknown | UNVERIFIABLE, UNKNOWN, PENDING, and any word not listed |
| `elevated` | The check found drift; acting on it needs care | DRIFT, WARN, STALE |
| `high` | The check failed or was refused | REFUTED, FAIL, FAILED, REFUSED, ERROR, BROKEN |

`REFUTED` is the one addition to the site's table; the contract's tolerance verdict needs it.

| Pole | low | moderate | elevated | high | ink | quiet |
|---|---|---|---|---|---|---|
| light | `#186844` | `#5c5a66` | `#8f5200` | `#b3261e` | `#15130f` | `#5d584e` |
| dark | `#8fdc8a` | `#a9a6b4` | `#f0a848` | `#ff7a6b` | `#ebe5d8` | `#9d978a` |

Grounds: light `#f4f3ef`, `#ebe5d8`, `#f2efe6`; dark `#060608`, `#070406`, `#1d1622`. Every level and ink token clears 4.5:1 WCAG contrast on every ground of its pole; `vectors/colour.json` checks all 30 pairs.

One hot mark per view: only the item with the highest liability is drawn in its colour (the first one on a tie). Every other mark is drawn in ink with its level in words. `hot_mark` picks the item. Meaning never depends on colour alone.

## 8. Sound

### 8.1 Canonical PCM

The hashed form is s16le PCM, interleaved, at a rate from the rate set. A float sample `x` quantizes as `floor(clamp(x, -1, 1) * 32767 + 0.5)`. The quantizer is applied once, at the end.

### 8.2 Reference and live paths

The reference for a sound is an offline renderer: it computes every sample in float64 and quantizes once. Python and JavaScript versions of the example score produce the same PCM (`692ead20...`). A live path (WebAudio `OfflineAudioContext` for checks, `AudioContext` for play) is reconciled against the reference with the PCM tolerance in section 6.3. It is never the reference: in the proof, nine WebAudio runs gave seven different PCM hashes, all within 1 LSB.

The seed rule applies per voice or event through sub-streams (`seed/voice-3`).

### 8.3 Loudness meter: `superstack-bs1770/1`

ITU-R BS.1770 integrated loudness:

1. K-weighting: a high-shelf biquad, then a high-pass biquad, per channel. At 48 kHz the coefficients are the standard's table as printed. Other rates derive the same filters with the constants libebur128 publishes (shelf f0 1681.974450955533 Hz, gain 3.999843853973347 dB, Q 0.7071752369554196; high-pass f0 38.13547087602444 Hz, Q 0.5003270373238773). At 48 kHz the derivation reproduces the table to within 1e-15.
2. Blocks of 400 ms with 100 ms hops (`rate*4/10` and `rate/10` samples). Block power is the sum over channels of the mean square, with weight 1 for both channels of a stereo signal.
3. Loudness of a power `p` is `-0.691 + 10 log10(p)`.
4. Keep blocks above -70 LUFS. The relative gate is the loudness of their mean power minus 10 LU. Keep blocks above it. The result is the loudness of the mean power of the kept blocks.
5. Every sum runs in index order. Python 3.12's `sum()` compensates floating-point error and would differ in the last bits, so the Python file uses plain loops.

The meter returns null when the signal is shorter than one block, when no block passes the absolute gate, for more than two channels, and for rates that are not multiples of 10 Hz (11025 Hz).

Checks: a 997 Hz sine at full scale reads -3.0103 LUFS, where the standard states -3.01 for 1 kHz; on the proof's sound this meter and ffmpeg 7.1 `ebur128` both read -20.7 LUFS. That is one signal and one agreement.

`peak_dbfs` is the sample peak. v0 does not measure true peak.

### 8.4 Loudness targets

| Class | Integrated | Peak | Source |
|---|---|---|---|
| `speech` (narration) | -16 LUFS within 1 LU | at most -1.5 dBTP | the narration pipeline that already ships |
| `music` (scores, trailers) | -14 LUFS within 1 LU | at most -1.0 dBTP | the trailer master that already ships |
| `interactive` (in-page sound) | at most -18 LUFS | sample peak at most -1 dBFS | inferred starting value, not yet tested with listeners |

`loudness_check(class, lufs, peak)` returns `verified`, `refuted` or `unverifiable`. It compares the sample peak with the true-peak ceiling. Sample peak never exceeds true peak, so a pass is necessary and not sufficient. A producer that claims a true-peak ceiling SHOULD measure it with a second meter (ffmpeg `ebur128=peak=true`) and name that meter in the receipt.

### 8.5 Accessibility

These rules bind every producer and every surface that plays sound.

1. No autoplay. Sound starts only from a user gesture.
2. Speech always has captions (WebVTT) and a transcript.
3. Reduced sound. When the reader asks for reduced motion, or turns a site-wide sound preference off, ambient and reactive sound does not start, and audio-reactive visuals show their still frame. Sound pauses when the tab is hidden unless the reader started playback.
4. Every sound has a visible text label and a stop control reachable by keyboard.

### 8.6 Audio receipt block

```json
"media": {
  "kind": "audio", "content": "speech", "rate": 48000, "channels": 1, "format": "s16le",
  "frames": 96000, "duration_flicks": 1411200000,
  "meter": "superstack-bs1770/1", "integrated_lufs": -16.2, "peak_dbfs": -3.1,
  "loudness_class": "speech", "loudness_verdict": "verified",
  "access": {"autoplay": false, "captions": "vtt", "transcript": true, "reduced_sound": "silent"},
  "narration": { ... }
}
```

The verifier enforces: a rate from the rate set, `s16le` with 1 or 2 channels, `duration_flicks` equal to `frames` times the flicks per sample, `autoplay` exactly `false`, `reduced_sound` either `silent` or `still-frame`, and for `content: "speech"` a non-empty `captions` and `transcript: true`.

### 8.7 Narration backends

A narration backend turns a script into speech. Every narration backend is an optional producer and never a reference: a reference must be reproducible by anyone, and a voice model's output is not.

A narration receipt carries a `narration` block:

| Field | Content |
|---|---|
| `backend` | The backend's name |
| `hosted` | `true` for a paid or remote service |
| `model` | Model name or version |
| `snapshot` | The dated snapshot or pinned revision, or null |
| `voice` | Voice id |
| `text_sha256` | SHA-256 of the UTF-8 script exactly as sent, with no normalization |
| `reference` | Always `false` |
| `reproducible` | Whether a rerun is expected to give the same PCM |

The PCM hash is the receipt's `content_sha256`. A hosted backend's output counts as reproducible only when its snapshot is pinned. When it is not, the receipt MUST say `reproducible: false`, and the verifier refuses it otherwise. Pinning is necessary and not sufficient: a pinned hosted model can still sample differently, so `reproducible` stays `false` until reruns have matched.

Known backends:

- Cartesia Sonic 3.6, pinned to the dated snapshot `sonic-3.6-2026-08-27`. A hosted, paid service that needs an API key; the key never enters a receipt or a repository.
- Qwen3-TTS, run locally (Apache-2.0 weights). GPU sampling is not bit-exact, so its receipts say `reproducible: false` unless reruns prove otherwise.
- Windows SAPI and Edge neural voices, as fallbacks. They are no longer the quality bar. Edge voices are a hosted service with no pinnable snapshot.
- A private voice model MAY serve as an optional backend. Its weights stay private, and it is never a reference.

Choosing a voice is a listening judgement, recorded apart from the receipt. Candidates read the same passage. The record covers naturalness, accent stability, warmth, name pronunciation, sentence rhythm, the absence of an exaggerated advertising delivery, and consistency over a longer passage. It names the provider, model snapshot, voice id, settings, script hash, audio hash, duration and licensing basis. Listening preference and technical signal checks are separate kinds of evidence.

## 9. Export formats

| Medium | Canonical (hashed) | Delivery | Byte-exact |
|---|---|---|---|
| Still | `frame.rgb8` or `frame.rgba8` | PNG, PPM; PFM for HDR | The canonical bytes, yes. A PNG container varies by encoder |
| Plot | SVG text | SVG, G-code | Yes |
| Video | Per-frame RGB24 chain hash plus the PCM hash | MP4 (libx264 and AAC) with `+bitexact` and one thread | Only with the same toolchain, which the receipt names |
| Sound | `pcm.s16` at the scene rate; f32le optional | WAV, FLAC, AAC in MP4 | WAV and FLAC decode to the canonical PCM. AAC does not |
| Notes | SMF events with the tempo map | MIDI format 0 | Yes |
| Weave | WIF 1.1 text | WIF | Yes |
| Paper | TeX source and PDF | PDF | With the same TeX bundle and source date |

v0 implements three writers, identical in all three files:

- `wav_s16(pcm, rate, channels)`: the 44-byte RIFF header (`fmt ` chunk of 16 bytes, PCM format 1, 16 bits per sample), then the samples.
- `ppm_rgb8(rgb, w, h)`: `P6\n<w> <h>\n255\n`, then the bytes. raw-native writes this header.
- `pgm_u8(gray, w, h)`: `P5\n<w> <h>\n255\n`, then the bytes.

FLAC and AAC go through ffmpeg. Their receipts hash the PCM before encoding and the container after. A FLAC receipt checks that the decode equals the canonical PCM; an AAC receipt states that the decode differs.

## 10. Conformance

| Vector file | Rule | Section |
|---|---|---|
| `canonical.json` | Numbers, strings, key order, rejections | 3 |
| `hash.json` | SHA-256, including the 55, 56, 63, 64 and 65 byte padding edges | 3.4 |
| `seed.json` | xmur3, mulberry32, sub-streams, `raw-pixel-hash/1`, site parity | 4 |
| `clock.json` | Flicks per frame and per sample, refusals | 5 |
| `receipt.json` | Building, sealing and verifying receipts, one case per error code | 6, 8.6, 8.7 |
| `reconcile.json` | Identity, PCM and RGB8 tolerance blocks, float RMSE, `round6` | 6.2, 6.3 |
| `colour.json` | OKLab both ways, risk tokens, contrast, verdict words, hot mark | 7 |
| `sound.json` | Quantizer, K-weighting, loudness on nine signals, targets | 8 |
| `export.json` | WAV, PPM and PGM bytes | 9 |
| `scene.json` | Scene hashes recorded by the proof, validation codes | 2 |

`vectors/MANIFEST.json` pins every vector file by SHA-256. Each runner checks those pins, runs every case, and counts its checks per file; CI requires the three counts to be equal, so no runner can skip a case. A crash inside a file is a failure, never a skip.

Each rule has a paired mutation per language in `tests/mutations.json`. `tests/mutate.py` applies each one-line break to a copy of the file, runs that language's vectors on the copy, and requires a failure from the vector file the pair names. A mutant that does not build counts as a harness error, never as a catch. The Python file uses `hashlib` for SHA-256, so it has no SHA-256 mutant.

## 11. Does not prove

- That any renderer is correct. The vectors show that three implementations agree with each other and with a few outside anchors. The pixel reference is raw-native's CPU path, and its own certificate refutes its screen-space AO against its ray-traced AO on the reference view.
- Equality across GPU vendors or drivers. Byte equality was observed on one RTX 4090 through ANGLE on Direct3D 11. SwiftShader differed on 9 pixels.
- That a sound sounds right, or how a device plays it. A PCM hash covers samples, not speakers.
- True-peak compliance. v0 reads sample peak.
- That the loudness targets suit listeners. They come from pipelines that ship, and the interactive ceiling is an inferred starting value.
- Anything about scenes beyond the shapes the vectors and examples use.

## 12. Changes

The contract id is `superstack/0`. Any change to a rule changes its vectors and the implementations together, in one commit, under a new release. A change that alters the bytes of an existing rule needs a new rule id, and the old id keeps working, as the legacy seed rules do.
